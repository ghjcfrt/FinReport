## 3. 一次运行的数据流及约束

### 3.1 输入冻结与提取边界

1. 用户选择一份报告，或显式指定关联报告集合。程序限制同公司、相同合并/母公司口径和会计准则；默认不合并四份比亚迪报告。
2. 检查扫描通过的本地 PDF 对象、文件哈希和已完成的提取任务。原生任务复用 `pdf_text/docling` 文本，OCR 任务只使用 OCR 文本，不借用文字层补充其结果。
3. 分别冻结报告总页数、选页、可用页、选页内无材料页和未选页。选页分析完成不代表整份报告完成。
4. 保存每个来源单元的报告、章节候选、原页、定位、原文及哈希。章节来自标题候选或继承，`boundary_verified=False`，不冒充已完成跨页表格/脚注重建。
5. 新核验要求读取该来源原页的已选上下文单元。整个原页超出预算时保留部分结果，不把被截断片段称为完整上下文。这仍不能保证跨页续表和下一页脚注完整。

原生整份事实已有显式自动校验按钮/API。新严格计算只查询真实 `auto_passed` 且来源可追溯的事实；旧复核记录、OCR 和选页候选均不能凭显示状态进入严格计算。OCR/选页的同等级自动准入尚待补齐。

### 3.2 章节、专题与未处理材料

白名单工具包括目录、词法检索、原文读取、相邻上下文、事实查询及确定性计算。跨章与跨报告取证只限冻结授权集合，不开放任意 SQL、路径、代码或外部网络。

引擎按报告登记九个财务专题：同比/环比、非经常性损益、政策估计与重述、合并范围、EPS、持续经营、利润现金流背离、利润至现金流调节表、经营现金流原因。后两项单独登记，避免把调节项当成经营原因。

材料台账区分已取回、实际曝光范围、处置与引用。没有读到的材料不能通过自报 `checked` 变成已检查；专题空答不能变成完成。未处理材料中性补查允许没有异常，允许提出新任务、支持、反证、限定、重复映射或无法判断。相关反证/限定使旧回执失效，并要求后续核验实际读取该材料。

默认预算：40 次模型调用、每任务 4 轮、12 个动态任务、每轮 6 个工具、24,000 字符请求上下文、10,000 字符来源片段、每任务 6 个单元、每批核验最多 6 条、1 轮修正、900 秒工作流预算。它们不是财报准确率目标；达到预算保存缺口。墙钟预算在步骤边界检查，不能强制中断一个持续流式返回的 HTTP 请求。

### 3.3 判断、核验与报告

每条候选独立编号并保留修订、主体/对象、期间、口径、单位、假设及限定。程序检查授权、逐字引用、边界、公式和结构；模型另判 `supported/partially_supported/insufficient_evidence/contradicted`。

核验执行失败、漏答 ID、坏 JSON 或断流使用独立执行状态，不伪装为财务“证据不足”。部分支持需要收窄为新修订重验。汇总新增判断重新核验；汇总冲突撤销相关回执，未解决时阻断发布。

最终 Markdown 由程序从核验通过的判断重建：正文逐字对应判断，保留适用口径、假设、限定、原文切片和计算 ID。模型自拟标题与自由理由不成为额外结论通道。报告列出选页范围、专题状态和未解决项数量；具体自由待办仍保存在候选工件。

发布门禁重查判断修订/哈希、原文和程序计算依赖、报告映射及冲突。离线回放按冻结事实重算 calculation，不相信结果自报 `auto_passed`。工件哈希匹配与报告可发布分别返回；`saved_artifacts_match` 不等于模型判断绝对正确。

## 4. 日志、故障与恢复

日志级别为 `TRACE/DEBUG/INFO/WARNING/ERROR/CRITICAL`，业务阶段另列。事件保留运行、任务、调用、判断、证据、计算、输入/输出工件、耗时、执行状态、错误码和后续动作。终端显示概要，完整脱敏输入输出和流式帧在工件中。

运行包位于配置的 `storage_dir/runs/chapter-{run_id}`。SQLite 保存权威事件与工件登记，JSONL、可读日志和 manifest 是投影。只允许读取已登记、路径合规且哈希一致的工件。关键记录无法持久化时停止后续新派发，并在 `%TEMP%/finreport-journal-emergency` 留最小脱敏通知。

已覆盖的恢复边界：

- 先持久预留数据库 ID，再初始化日志，防止失败后 ID 被复用到孤儿日志目录。
- `queued → running` 原子认领，同 ID 重投不重复派发；父 run 显式续跑也原子认领。
- 已派发但结果未知、流式不完整或关键工件损坏时，不自动重发或接纳残缺结果。
- 续跑创建新 run，将父 run 授权且完整的嵌套工件导入，新包可独立回放；父 run 保持原始记录。
- 输入、授权集合、模型配置或请求格式变化时拒绝无条件沿用旧状态；v1 提示词/回执不被 v2 静默重写。
- 日志构造失败或错误事件二次失败，数据库仍落 `failed`，避免永久卡在 `running`。
- 桌面日志按序号分页并在终态排空，防止只看到前 250 条；旧任务迟到的结果不覆盖当前任务。

取消是协作式的：停止后续步骤，已发往供应商的请求可能继续结束。尚未实现分布式租约/fencing、进程崩溃自动接管或独立强制 HTTP 总时限。百度旧异步 OCR 请求也没有全部接入新统一 journal；不能宣称所有历史提取链路已完成日志迁移。

### 6.3 对问题的处理

核验提示词新增 `claim_evidence_verify_v2`，明确：缺支持与有反证不同；反证须在同主体、期间、口径和限定下给出相反依据；reason 也不能引入未登记外部规则/事实或自行派生新数值，需要工具结果或具体补查。

这是通用边界约束，不是仅拦截“非金融资产类”的个例补丁。旧 v1 提示词和 A/B 原始工件保持原样；新运行用 v2，旧检查点/回执仍按 v1 回放。v2 的离线合同与兼容行为已测，但**没有用第三次真实请求验证语义改善**，不能将提示词变更写成已经消灭问题。

核验 reason 不直接进入成立报告；成立正文仍需映射已核验 claim。模型如果错误地批准一个附真实无关引用的 claim，当前合同仍可能漏放，这需要独立评测和进一步约束，不能用哈希自证语义。
